# Financial invariants

FinGuard uses PostgreSQL as the financial source of truth. Migrations `20261031_0001` and `20261031_0002` established and tested database guards; `20261031_0003` adds a nullable transaction memo and an ordered status-history table. It preserves both older revisions and their financial triggers. The new migration refuses downgrade with SQLSTATE `P0001` while status history contains rows, protecting audit data. The migration cycle runs only on the separate empty `finguard_migration_test` database.

Revision `cfe7aacc2d92` adds users, auth sessions, hashed refresh tokens, auth audit rows, and nullable `accounts.owner_user_id`. It preserves all existing accounts, transactions, and triggers. Its downgrade refuses to discard security data or owned accounts. New customer wallets must have an owner. Legacy unowned wallets and system accounts are inaccessible to customer APIs. A customer's transfer source and reversal source must be owned by that active user; authorization is checked before idempotency replay. These are application-level protections and depend on using the API rather than direct privileged SQL writes.

- Money is integer minor units. Supported currency codes are USD, EUR, GBP, and INR. There is no FX conversion.
- Wallets are liability accounts. Their balance is the sum of **posted credits minus posted debits**. The balance is computed with SQL aggregation, never stored as a mutable authoritative field.
- Internal opening funding debits the settlement asset and credits the customer liability. Wallet-to-wallet transfer debits the sender and credits the recipient.
- A posted journal is balanced in its single transaction currency and has at least two valid lines. Deferred PostgreSQL triggers reject empty, unbalanced, or invalid reversals at commit. Posted headers and lines are immutable under direct SQL.
- The application locks both wallets in UUID order before computing a balance and posting, preventing concurrent service requests from overdrawing one wallet under `READ COMMITTED`. The database triggers guarantee journal balance, while overdraft prevention depends on service access discipline.
- The application lifecycle is `received → pending_risk → approved → posted|failed`, with `pending_risk → challenged|blocked` alternatives. Terminal states cannot transition again through the service. Each transition gets a sequence and reason code in `transaction_status_history`.
- Blocked, challenged, and failed transfers have no journal. An allowed transfer, risk decision, journal, outbox event, and stored idempotency response commit together. Database failures roll them all back.
- A reversal is a **new** mirrored posted journal tied to its original. The original transaction stays posted and is reported as reversed through the linked entry. A second reversal is rejected.
- Idempotency is scoped by operation and key in PostgreSQL. The unique constraint and conflict handling serialize concurrent duplicate claims. Replays return the exact stored status and body; different requests using the same key fail.
- Outbox rows are created in the same commit as the state they describe and start unpublished. The dispatcher publishes asynchronously; consumers use a PostgreSQL inbox and at-least-once delivery semantics.

These behaviors are supported by PostgreSQL integration tests for the exercised operations, authentication/authorization paths, and concurrent schedules. They do not establish protection from direct privileged database writes, all possible schedules, or production readiness.

## Event processing invariants

| Invariant | Enforcement | PostgreSQL test evidence / status |
| --- | --- | --- |
| Outbox event IDs, payloads, and event metadata persist with the transaction outcome; a failed transaction does not commit its outbox insert. | Database transaction boundary in the application. The database does not verify semantic coupling between every business row and an outbox row. | Atomic transaction and outbox behavior exercised by PostgreSQL financial integration tests. |
| A publisher failure retains its original outbox row for retry or dead-letter inspection; dispatch does not delete it. | Application worker behavior; no delete-on-failure path. | PostgreSQL dispatcher retry/dead-letter tests. |
| Claims have an owner, finite expiry, and monotonically incremented generation. Concurrent claims skip locked rows. | Application SQL with PostgreSQL row locking and persisted claim fields; no database trigger independently enforces the lifecycle. | PostgreSQL concurrent claim, expiry, and generation tests. |
| Claim-dependent publish-state, retry, dead-letter, renewal, and release updates require matching event/request ID, owner, generation, claimed status, and a lease later than PostgreSQL `clock_timestamp()`. | Application conditional SQL predicates using database time. | PostgreSQL stale-owner and lease tests; replay stale owner tests cover completion, retry, dead-letter, renew, and release. |
| Network publication runs outside the database claim transaction, and the worker records success only after the publisher call returns successfully. | Application worker control flow. A broker acknowledgement's exact durability meaning depends on Kafka configuration. | FakePublisher flow and PostgreSQL state tests; live Kafka behavior is **not verified**. |
| Delivery is at least once. A crash before publish is recoverable after lease expiry; a crash after acknowledgement but before database update can cause duplicate publication. Exactly-once delivery is not claimed. | Application lease recovery plus broker/database boundary. | PostgreSQL lease recovery and FakePublisher crash-window tests; live Kafka behavior is **not verified**. |
| Consumer inbox identity is unique per `(consumer_name, event_id)`, and an event ID can be independently processed under a new consumer identity/version. | PostgreSQL unique constraint plus consumer application logic. | PostgreSQL tests verify duplicate suppression and version-scoped inbox rows. |
| Consumer database processing commits before Kafka offset acknowledgement. | Consumer adapter control flow. | Code path inspected; no live Kafka/offset integration test was run. This ordering is **not verified against a broker**. |
| Administrative replay requests retain requester, reason, idempotency identity, state, attempt count, and error outcome. Requests are retained when completed or dead-lettered. | PostgreSQL constraints/foreign keys and application API/worker lifecycle; there is no database trigger enforcing status transitions. | PostgreSQL API and replay worker tests verify persistence, retry, completion, and dead-letter retention. |
| Replay lifecycle is `pending → claimed → completed` on success, or `claimed → retry_scheduled → claimed` until completion/dead-letter. Expired claims can be reclaimed with a higher generation. | Application worker state transitions persisted in PostgreSQL. | PostgreSQL tests cover success, retry eligibility, exhaustion, lease recovery, and fencing. |
| Transport replay republishes the original event ID and unchanged envelope content; replay processing does not edit or delete the outbox row or delete inbox history. | Replay worker/application convention. Outbox event immutability and inbox-history preservation are not protected against privileged direct SQL writes by an immutability trigger. | PostgreSQL/FakePublisher tests compare original payload and creation time and verify consumer deduplication. Broader immutability is **not database-enforced**. |
| Historical reprocessing uses a new consumer identity/version; it does not delete the previous consumer's inbox rows. | Application deployment/versioning convention. | PostgreSQL tests verify separate uniqueness scopes and retained rows. Reprocessing behavior beyond inbox identity is **not independently verified**. |

Kafka is not required to start the API. PostgreSQL and FakePublisher tests do not establish successful live broker delivery, offset commits, or broker durability. **Live Kafka integration: NOT RUN.**

## Behavioural feature invariants

| Invariant | Enforcement | Test evidence / status |
| --- | --- | --- |
| Only committed `transaction.posted` events produce activity; source/destination, amount, and currency are checked against the posted PostgreSQL transaction. | Consumer application validation; old event payloads obtain account IDs from the transaction row. | PostgreSQL projection-consumer tests. |
| Both account projections update atomically with the event-ID fingerprint and event metadata. Same ID/same content is a duplicate; same ID/different content is rejected. | Redis Lua script. This guarantee depends on an available standalone Redis server; Redis Cluster is unsupported. | Live Redis 8.6.8 tests cover source/destination projections, concurrent events, key-type preflight failure, duplicate fingerprints, and namespace isolation. |
| Projection writes happen before the PostgreSQL feature inbox commit, which precedes Kafka offset acknowledgement. Redis success followed by inbox failure is recoverable by redelivery without double counting. | Application protocol across Redis and PostgreSQL; the stores do not share an ACID transaction. | Live Redis plus PostgreSQL tests inject an inbox commit failure, redeliver, and verify a successful inbox commit. A fake transport verifies commit-after-success ordering; Kafka offsets were not tested against a broker. |
| Redis failure does not change ledger/outbox state and does not acknowledge the feature event. The consumer retries the same message before polling a later offset. | Separate consumer process and explicit commit-after-success loop. | PostgreSQL confirms an unavailable Redis endpoint leaves the posted transaction intact and creates no feature inbox row; live Kafka offset behavior remains unverified. |
| Feature windows use UTC event time and `[t - window, t)` boundaries, exclude the event at `t`, and isolate currencies. Amounts stay integer minor units; average/variance are analytics-only float values (population variance). | Shared pure Python calculator and registry. | Live Redis projection parity against the offline calculator covers all configured windows, exact lower boundaries, scoring-time exclusion, out-of-order events, currency, direction, counterparty counts, aggregation, and population variance. |
| Redis retains 14 days of account event detail; online `as_of` requests are supported for the latest 7 days. Deduplication fingerprints live for the projection lifetime because outbox/replay history has no enforced purge horizon. | Redis TTLs and projection namespace design. | Live Redis adapter tests and AOF restart/redelivery acceptance passed; dedup records survived the tested container restart. |
| Historical reconstruction reads posted outbox events joined to posted transactions and standard posted journals. Rebuilds use a separate namespace, keyset ordering, event-ID idempotence, progress state, live dual-write, explicit ADMIN activation, and pre-activation feature comparison. | PostgreSQL source query plus application rebuild workflow and Redis projection controls. | PostgreSQL and live Redis tests verify dual-write while rebuilding, progress, database parity, failed-parity activation rejection, and recovery activation after simulated active-namespace loss. |
| Feature reads are limited to ANALYST and ADMIN; customer feature reads and all customer projection mutation are denied. Missing/unavailable Redis returns degraded/unavailable status and does not block financial APIs. | Existing RBAC dependencies and feature API/consumer separation. | PostgreSQL API authorization and transaction tests; an unavailable Redis endpoint left the posted transaction unchanged and no feature inbox row was committed. |

Available activity signals are transfer amount, currency, occurrence time, source account, and destination account. Merchant, device, and IP signals are not present. Live Redis verification is limited to the local single-container development service; it does not establish replicated failover, Redis Cluster behavior, or Kafka delivery.
